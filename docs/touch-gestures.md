# Жесты на тач-устройствах: как это устроено и что нельзя ломать

> **Обновлено:** 2026-09-24

Самое хрупкое место редактора: за одну сессию оно ломалось дважды, причём оба раза правки по отдельности были верны, а вместе давали регресс. Ниже -- инварианты, которые надо держать в голове, прежде чем сюда лезть.

Основной сценарий: школьник на iPad решает задачу пальцем или Apple Pencil. Значит цена ошибки здесь выше, чем в любом десктопном пути.

---

## Два потока событий, и это главное

Браузер на тач-устройстве шлёт **оба** семейства одновременно:

|  | что несёт | частота |
| --- | --- | --- |
| `pointerdown/move/up` | ОДИН указатель на событие | по событию на палец |
| `touchstart/move/end` | ВСЕ касания разом (`event.touches`) | одно событие на кадр |

Порядок на iOS: `pointerdown` -> `touchstart` -> `pointermove` -> `touchmove`. То есть pointer идёт первым, и к моменту touch-события состояние пера уже известно.

### Почему это важно

Пока двупальцевое преобразование считалось по pointer-событиям, координата одного пальца всегда была свежей, а второго -- отставшей на шаг. Расстояние между пальцами меряется по разновозрастным точкам и «дышит» даже при строго параллельном переносе.

Замер: пальцы в `(100,100)` и `(300,100)`, чистый сдвиг на 50 px вдоль их линии -- масштаб проседает **1 -> 0.75 -> 1**. Пользователь видит это как дрожание.

**Поэтому преобразование считается в `handleTouchMove`** (`driveGestureFromTouches`), где обе координаты одновременны.

---

## Разделение обязанностей

| Кто | За что отвечает |
| --- | --- |
| pointer-события | **учёт пальцев** (`gesture.pointers`), палм-режекция, сессии панорамирования |
| touchmove | **преобразование** (пан + зум) при двух прямых касаниях |

[!] **`gesture.pointers` обязан наполняться из pointer-событий.** На нём висит `isTouchScreenMultiTouchGesture()` -- единственный предохранитель, отключающий на iPad собственный `gesturechange` Safari. Перестанешь наполнять -- получишь двойной зум.

Пока touch-путь ведёт жест (`touchGesture.driving`), ветка пинча в `handleCanvasPointerMove` **молчит**, иначе преобразование применится дважды.

## Инварианты, которые нельзя нарушать

### 1. Множителя 2 в touch-пути нет и быть не должно

В pointer-ветке пинча стоит `2 * deltaX` с комментарием «magic number». Это **не** геометрия: геометрия центра самокорректируется, два события за кадр в сумме дают полный шаг. Множитель латает **потерю одного из двух батченных обновлений**: `translateCanvas` получал объект с абсолютными координатами, React батчил два pointermove, оба читали одну базу, второй перетирал первого. Апстрим подогнал множитель «на глаз» под жалобу «two finger panning is slow» (#7849), не разобравшись.

В touch-пути событие одно на кадр, терять нечего -- множитель дал бы двукратный перебег. Тест `touchGesture.test.tsx` проверяет соответствие 1:1.

### 2. Абсолютные значения в `translateCanvas` -- только из свежего состояния

Объектная форма `this.setState({ scrollX: this.state.scrollX - delta })` считает цель от снимка, который может отставать на кадр. Пиши функциональную форму:

```ts
this.translateCanvas((state) => ({
  scrollX: state.scrollX - delta / state.zoom.value,
}));
```

Симптом нарушения: «холст едет несоразмерно движению пальца». [!] В jsdom это НЕ воспроизводится -- троттлинг там синхронный, а состояние не отстаёт. Проверяется только на живом устройстве.

### 3. Безусловно рвёт сессию только ПЕРО

`maybeCleanupAfterMissingPointerUp` получает событие, чтобы адресат решил по `pointerId`, его ли это указатель: новый контакт не должен рвать чужую живую сессию (иначе второй палец убивал панорамирование первого).

Исключение -- перо: оно забирает поверхность себе, и ладонь, легшая первой, обязана лишиться сессии, иначе перо не начнёт штрих.

Проверяется `tabletInputPolicy.test.tsx` -- **37/37 обязательны**.

### 4. `gestureCollapsePan` только при отсутствии настоящей сессии

При распаде жеста с двух пальцев до одного оставшийся палец продолжает панорамировать: под выделением своей сессии у него нет (рисование ему отменили в момент появления второго пальца), и без этого холст просто замирал бы.

[!] Но под **рукой**, pen mode и просмотром сессия ЕСТЬ и переживает жест. Тогда `gestureCollapsePan` обязан молчать (`!isPanning`), иначе сдвиг применяется дважды и холст едет ровно вдвое быстрее пальца.

### 5. `shouldCacheIgnoreZoom` -- только когда масштаб реально поехал

Флаг велит рисовать элементы из растрового кэша, снятого при другом масштабе. На пинче это оправданная экономия, при чистом перемещении -- мыло и «плывущая» картинка.

### 6. Режим пера включается один раз и только если пользователь его не выключал

Первое касание пером -- на холсте (`handleCanvasPointerDown`) или на кнопке тулбара (`Actions.tsx`, в rAF после `change`) -- идёт через `detectPen()`: `penDetected` становится `true`, `penMode` -- `penModePreference !== false`. Повторно `detectPen()` ничего не делает, выход из режима только ручной.

`penModePreference` -- явный выбор пользователя кнопкой режима пера (`togglePenMode(null)`); хост хранит его в аккаунте и засевает через `setToolSettings`. Программный `togglePenMode(true|false)` предпочтение не трогает. При `false` перо определяется, кнопка режима появляется выключенной, палец остаётся инструментом. Проверяется `toolSettingsApi.test.tsx` и `tabletInputPolicy.test.tsx` (раздел auto pen mode).

## Порог намерения: перемещение против масштабирования

Дрожание руки нельзя убрать точной математикой -- оно есть во входном сигнале. Работает **переключение режимов**, а не статичный порог:

- пока жест признан перемещением, масштаб **заморожен** -- дрожание в него не попадает вовсе;
- расстояние отсчитывается от **якоря**, а не покадрово: тремор колеблется вокруг якоря и порога (`ZOOM_ENGAGE_PX = 10` экранных px) не берёт, осознанный пинч набирает смещение за кадр-два;
- когда расстояние перестаёт меняться (`ZOOM_SETTLE_FRAMES = 3` кадра с изменением меньше `ZOOM_SETTLE_PX = 1.5`), жест возвращается к перемещению;
- на каждом переключении точка отсчёта пересчитывается -- скачков нет.

[!] Что НЕ работает (проверено на живом устройстве, забраковано founder'ом):

- **жёсткое вычитание мёртвой зоны** -- разрыв производной, вход в пинч ощущается рывком;
- **плавная ступенька (smoothstep)** -- пропускает дрожание в средней полосе;
- **односторонний порог** без возврата в режим перемещения -- жест «залипает».

Ориентир: в iDroo жест «не замечаешь» именно потому, что он быстро распознаёт намерение и **так же быстро возвращается обратно**.

jsdom 22 даёт `TouchEvent`, но не `Touch`: плоские объекты в `touches` проходят как есть, полифилл не нужен. `touchType` (`"direct"` / `"stylus"`) jsdom не синтезирует -- подставляется руками.

## Чего тестами не проверить

Живой iPad нужен для: ощущения плавности, реального тремора, палм-режекции с Apple Pencil, порядка событий iOS и отставания состояния React (пункт 2 выше). **Любая правка в этом файле требует живой приёмки**, зелёные тесты её не заменяют.
